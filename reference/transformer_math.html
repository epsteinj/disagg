How to read this page

This is a chip-vs-chip evaluation for production LLM inference. Pick a workload preset (or set custom inputs), select chips, and see which silicon wins each scenario.

1 · Set the workload

The workload preset dropdown auto-fills T, SLO, TTFT, I:O, and KV precision for common production patterns. You can override any individually.

  • T — context length (input tokens per request). Chat ~4k, RAG ~32k, summarization ~128k.
  • SLO — per-user output streaming speed (tok/s). Chat 30, voice 80, autocomplete 100.
  • TTFT — max time-to-first-token (prefill duration in sec). Autocomplete 0.2s, RAG 5s, summarization 30s.
  • I:O ratio — input:output tokens per request. Chat 1:1, RAG 10:1, summarization 30:1.
  • Precision — weight storage (FP16 / FP8 / FP4). Chips fall back if not natively supported.
  • KV precision — independent of weight precision. Production widely uses FP8 KV.

2 · Read the comparison table

  • Derived B — concurrent users this chip serves per replica at the SLOs. Subscript shows which SLO is binding: tok/s (decode-bound), TTFT (prefill-bound), or both. SLO unmet means even B=1 can't meet the SLOs at any cluster size.
  • Fits? — TP cluster size (number of chips per replica) — auto-derived to meet the SLOs at the chosen B.
  • Prefill / Decode / Effective tok/s — aggregate throughput per replica. Effective is the I:O-weighted harmonic blend.
  • $/M capex — chip capex amortized 3 years 24/7. Bare hardware only.
  • $/M all-in — capex + power × PUE 1.3 × $0.10/kWh. Closer to true operating cost.
  • Tok/kW — power efficiency. Important in power-binding datacenters.
  • Binds — bottleneck axis: compute / weights / KV / interconnect / balanced.

  • Per-replica framing: total user capacity = B × replicas is a deployment choice; not bound here. Use the Throughput-matched view (full calculator) for replica-scaling.

How to read this tool — start here

Why this exists. AI chip companies make wildly different claims — Cerebras claims 30× faster inference; Tensordyne claims 5× tokens/watt; Positron claims 2T-parameter models on one chip. This tool lets you plug a real model + workload into each chip's published specs and see which claim survives.

The 4 things to play with (top section just below this):

  • Workload = what the chip is doing. Inference (serving an existing model), MoE inference (sparse expert routing), Training (gradient updates), Diffusion (image/video).
  • Phase = which part of the workload. Inference splits into prefill (processing the input prompt — fast, parallel, compute-bound at long context) and decode (generating output tokens one at a time — slow, serial, memory-bound). Training has forward / backward / optimizer.
  • Chip = which silicon to evaluate. The architecture diagram on the right updates as you pick.
  • Model (in the calculator further below) = what's actually running. Llama 70B is the baseline; DeepSeek V3 and GPT-5.5 are frontier MoE; Mixtral / Qwen / Gemma are mid-size.

The metrics you'll see, in plain English:

  • tok/s aggregate (throughput view) = total output tokens/sec across all concurrent users. Optimized for batch APIs, async pipelines, data labeling. Bigger batch → bigger aggregate.
  • tok/s per user (interactivity view) = how fast each individual user sees tokens streaming. Critical for chat/voice/agents — fluent reading needs ≥ ~25-30 tok/s/user. Bigger batch → divides this.
  • TTFT (time to first token) = how long the user waits from sending the prompt to seeing the first reply. Critical for chat / autocomplete.
  • $/M tokens = dollars of chip-cost amortized over 3 years to produce 1 million tokens. The closest thing to "cloud inference price" the tool produces. Lower is cheaper.
  • tok/$ = inverse framing of $/M (higher = better, easier to compare against tok/kW).
  • tok/kW = throughput per kilowatt of system power. Matters when datacenter power is the binding constraint.
The throughput-vs-interactivity trade-off: at decode (memory-bound), raising batch B multiplies aggregate throughput but divides per-user throughput by the same factor. Same memory read, more tokens written. Pick which optimization target matches your workload — they're at opposite ends of the same axis.

The key parallelism schemes (shown in the "Multi-GPU" panel during the walkthrough):

  • TP (Tensor Parallel) — each chip holds 1/N of every layer's weights and computes its shard. Synced via all-reduce at end of attention + FFN. Used when one chip can't fit the model.
  • DP (Data Parallel) — each replica holds the full model, serves different requests. Synced via gradient all-reduce at end of training step (no comm for inference).
  • EP (Expert Parallel) — for MoE, different experts live on different chips. Tokens dispatched via all-to-all to their assigned chips, gathered back. The all-to-all is what hurts SRAM-only chips on huge MoE.
  • PP (Pipeline Parallel) — different layers on different chips, tokens flow through serially. Mainly used during training; Groq's whole inference architecture is pipeline-parallel.

How transformer data moves through B200, one layer

  1. Weights pulled from HBM → L2 → L1 → registers. The kernel launcher tiles each matmul (Q, K, V, O, up, gate, down) into chunks the SM can hold. Tile sizes are chosen so the working set fits in shared memory + registers.
  2. Tensor Cores execute the matmul on the tile. A single Tensor Core op multiplies a small matrix (e.g. 16×16) in 1 cycle. The SM's 4 Tensor Cores work in parallel; 74 SMs × 2 dies × 4 cores per SM = ~600 Tensor Core instances on chip.
  3. Partial results stay in registers/shared memory. FlashAttention exploits this: the score matrix Q·K^T is computed, scaled, softmaxed, and multiplied by V all inside SRAM, never materializing the full [T × T] matrix in HBM.
  4. Outputs stream back to HBM as activations (and as K, V into the cache during prefill).
  5. L2 acts as a recycling buffer for tiles being reused across SMs. With ~63 MB per die (126 MB total), it can hold a meaningful slice of weight tiles but not whole matrices.
During Prefill (compute-bound)
  • Many tokens flow through each layer in parallel.
  • Per-tile arithmetic intensity is high — Tensor Cores saturated.
  • Weight read from HBM is amortized across many tokens.
  • Bottleneck: Tensor Core throughput (~10 PFLOPS fp8 on B200).
  • KV cache is being written, not read.
During Decode (memory-bound)
  • One token per request, per step. Tiny matmuls.
  • Same ~140 GB of weights read from HBM per token.
  • Plus the full KV cache (linear in T) read every layer.
  • Bottleneck: HBM bandwidth (7.7 TB/s).
  • Tensor Cores mostly idle; SMs wait on memory.
  • Only batching amortizes the weight read across users.
During Training (forward + backward + optimizer)
  • Forward: same Tensor Core path as prefill. Activations cached in HBM for backward (~B·T·d·L bytes per replica — large enough that gradient checkpointing is often used).
  • Backward: same kernels run reverse; ~2× forward FLOPs. Weight gradients written back to HBM. Per-block TP all-reduces ride NVLink 5 @ 1.8 TB/s intra-NVL72 (cheap); inter-NVL72 falls to IB/Ethernet ~100 GB/s.
  • Optimizer (Adam): pure memory traffic. Read W + g + m + v, write W + m + v — ~7× weight bytes per param. FP32 moments dominate footprint (8 bytes/param) regardless of training precision.
  • End-of-step DP gradient all-reduce: ~140 GB per replica for Llama 70B FP16. This is the bandwidth-binding step at multi-rack scale.
  • Total memory: weights + grads + 2× FP32 moments + activations ≈ 5-6× model size — forces multi-chip TP even for 70B-class.

How transformer data moves through TPU Ironwood

  1. Each chiplet operates on its own HBM space. The compiler partitions the model across chiplets and chips at compile time — no runtime cache coherence.
  2. The 128×128 systolic MXU consumes a tile per cycle. Weights stream from HBM into the MXU via on-chip scratchpad memory (CMEM/VMEM); operands flow systolically through the array.
  3. SparseCore handles embedding lookups in parallel — designed for recommendation but used aggressively for token-embedding gather during prefill.
  4. At pod scale, ICI links chips in a 3D torus. The OCS switches physically reconfigure which slices talk to which, enabling all-reduce / all-gather patterns at 9,216-chip scale.
  5. No L2-style cache. All on-chip memory is software-managed scratchpad — the XLA compiler decides what lives where. Different bandwidth/latency tradeoffs than NVIDIA's hardware-managed hierarchy.
During Prefill
  • Compiler tiles attention/FFN matmuls across chips.
  • MXUs saturate at full systolic throughput.
  • OCS topology reconfigured per workload.
  • Bottleneck: MXU FLOPS at full pod scale.
During Decode
  • Per-chiplet HBM bandwidth (7.37 TB/s) bounds decode throughput.
  • KV cache distributed across chips in a pod.
  • ICI all-reduce for cross-shard attention.
  • Bottleneck: HBM bandwidth + ICI latency.
During Training
  • Forward: MXUs saturate at BF16/FP8. Activations cached across the pod, sharded via SPMD (XLA compiler decides).
  • Backward: ~2× forward FLOPs. 3D-torus ICI @ 1.2 TB/s/chip handles TP all-reduce of activation gradients. This is where TPU pods shine — collectives scale near-linearly to thousands of chips.
  • Optical Circuit Switching (OCS) reconfigures topology per workload, so multi-pod gradient all-reduces don't bisection-bottleneck.
  • Optimizer: SparseCore + TensorCore handle Adam updates on dense and embedding tables respectively. Pod-scale optimizer rarely dominates step time — collectives + compute do.
  • The TPU is the strongest standalone training fabric in this comparison (used for all Gemini training at Google).

How transformer data moves through MI355X

  1. Weights pulled from HBM into Infinity Cache (256 MB) — much bigger than NVIDIA's L2, lets larger tiles stay on-chip across XCDs.
  2. Tiles routed through IODs to XCDs. The IOD layer is the traffic cop — handles cross-XCD coherence and HBM routing.
  3. Matrix Cores execute the matmul in FP4/FP6/FP8 (new in CDNA 4) or BF16.
  4. 8-GPU all-to-all over Infinity Fabric — every GPU in a server connects directly to every other GPU at 112 GB/s per link.
  5. ROCm + vLLM/SGLang handle the software stack — first-class support since ROCm 7.
During Prefill
  • Tile flows: HBM → Infinity Cache → XCD CU → Matrix Core.
  • FP8/FP6 saturate Matrix Cores at large batches.
  • Bottleneck: Matrix Core throughput.
During Decode
  • Full 288 GB / 8 TB/s HBM read for every weight per token.
  • Infinity Cache helps only for hot tiles (small share at decode).
  • Bottleneck: HBM bandwidth.
  • 288 GB capacity lets longer KV caches fit without sharding.
During Training
  • Forward: same Matrix Core path as prefill. 288 GB per chip is generous for activation cache — Llama 70B training fits on a single chip for state.
  • Backward: same kernels reversed. ~2× forward FLOPs. Infinity Fabric @ 896 GB/s handles intra-rack (8-chip HGX) TP all-reduce. Multi-rack DP all-reduce goes over RoCE — same fabric tax as NVIDIA.
  • Optimizer: 8 TB/s HBM (slightly higher than B200) → optimizer step is marginally faster per chip. Adam state (FP32 m + v) eats ~560 GB for Llama 70B — fits in just 2 MI355X chips capacity-wise.
  • Software: ROCm 7 training kernels are production-grade as of 2025. Used at scale by MSFT, Meta, Oracle.

2. Precision & fallback chain

If a chip doesn't natively support the requested precision, it falls back to the highest supported format — and pays the cost in BOTH compute (lower throughput) AND memory (more bytes per param).

Weight precision fallback (per chip)
ifchip supports requested precision→use it
else ifrequested = FP4 and chip supports FP8→fall back to FP8
else→fall back to FP16
KV cache precision (INDEPENDENT of weight precision)
ifKV precision = "match weights"→use weight effective precision
elseresolved against chip support, same fallback chain (FP4→FP8→FP16)→use chosen KV precision
In production (2024-2026), KV is widely quantized to FP8 regardless of weight precision — vLLM, TensorRT-LLM, SGLang all support this. Halves KV memory + BW vs FP16 KV with negligible quality loss for most models. FP4 KV is Blackwell-era and accuracy-risky; FP16 KV is the legacy baseline. Long-context workloads (RAG 32k, summarization 128k) benefit most because KV dominates HBM at high T.

3. Cluster sizing (N_chips)

How many chips are needed to hold the model + KV cache. If one chip can't fit it, the cluster shards via tensor parallelism (TP).

Component sizes
modelbytes
= Nparams × bytesper_val(weight)
Tmax
= Tinput × (1 + 1 / ioRatio) — prompt + generated output
KV cache holds the entire sequence — prompt AND generated output. During prefill, K/V are computed for every input token and stored. During decode, each new token's K/V is appended (cache grows by 1 per step). The cache must be sized for the maximum final length: Tmax = input + output. For chat (I:O 1:1), Tmax ≈ 2 × Tinput. For RAG (I:O 10:1), Tmax ≈ 1.1 × Tinput. The capacity ceiling reserves Tmax per user; decode reads from a Tmax-sized cache; prefill compute uses Tinput.
kvper_user
= Tmax × 2 × (Hkv × dk) × L × bytesper_val(kv)
Weights and KV use independent precisions. The "2" covers K and V tensors. For MLA models (DeepSeek V3, Kimi K2) this collapses to a single latent dimension — ~50× smaller per token. Modern production: FP8 KV regardless of weight precision (halves KV memory + BW from the legacy FP16 baseline).
kvtotal
= kvper_user × B
trainingextra
= modelbytes(grads) + 8 · Nparams(Adam m+v) + 0.5 · B · T · d · L · bytesper_val(act cache)
Training only. The first modelbytes term inside trainingextra represents gradients (one model-bytes worth). The 8 · Nparams term = Adam m + v moments (each FP32 = 4 bytes/param × N_params). The last term is the activation cache. KV cache is set to 0 for training (KVs are recomputed each forward pass, not persisted across optimizer steps).
Cluster size
totalcapacity
= modelbytes + kvtotal + trainingextra
Nchips
= ⌈ totalcapacity / chip.memcap ⌉

4. Per-step compute & memory

Each layer is decomposed into 16 steps (LLM) or 21 steps (MoE: adds router / dispatch / experts / combine / gather). For each step, compute the FLOPs and bytes touched, then translate to time using the chip's peak compute and memory bandwidth (sharded across N_chips).

For each of the 16 (LLM) or 21 (MoE) steps
flops
= step-specific FLOP count
bytestotal
= (bytesweight + bytesact + byteskv) × bytesper_val
Time per step
tcompute
= flops / (chip.peak × Nchips)
tmemory
= bytestotal / (chip.membw × Nchips)
tstep
= max( tcompute , tmemory )
max() assumes compute and memory fully overlap — the binding axis sets the step time. Standard roofline approximation; real workloads see partial overlap.

6. Throughput

Tokens generated (or processed, for prefill) per second.

tpsdecode,agg
= B / tpass — all B users combined
tpsdecode,user
= 1 / tpass — one user's stream rate
tpsprefill,agg
= (B · T) / tpass — B users × T input tokens per pass
Aggregate is the system-throughput metric (drives $/M tokens). Per-user is the interactivity metric (drives SLO satisfaction). They trade off — bigger B raises aggregate, lowers per-user.

7. SLO-derived batch B per chip per scenario

B is a per-replica property of the chip — how many concurrent users a single cluster serves. Total user capacity = B × replicas is a deployment choice (exogenous to chip evaluation), so it isn't bound here. Two SLO axes:

SLO inputs (both optional; either or both can be active)
SLOtps
= target per-user output tok/s (decode streaming rate). Sets max acceptable tpass.
SLOttft
= max acceptable time-to-first-token (prefill duration in seconds).
Different workloads care about different axes. Decode-heavy (chat, voice, code-gen) → SLOtps is the binding constraint. Prefill-heavy (RAG, summarization, agentic) → SLOttft often binds first because 32k+ context prefill takes seconds. The calc enforces both when both are non-zero.
Mode 1 — Latency-bound (at least one SLO > 0)
B
= max B such that ∃ N meeting both SLOs at (B, N)
Nchips
= min N ≥ Nmin-fit(B) such that 1 / tpass,decode(B, N) ≥ SLOtps AND tpass,prefill(B, N) ≤ SLOttft
Two-level search. Outer: binary search over B in [1, 16,384]. Inner: for each candidate B, find the smallest Nchips ≥ minimum-fit that meets BOTH SLOs (capped at 8× minimum-fit or 128 chips, whichever is smaller). Models real production: providers over-provision TP beyond min-fit for latency, and prefill-heavy workloads need TTFT bounds that single-chip clusters often can't meet (e.g., 128k context on 1 chip might take 60s of prefill — over the 30s summarization budget — forcing TP=4+).
binds
= 'latency' (either or both SLO axes were the binding constraint)
edge case
'latency-violated' if no (B, N) pair meets BOTH SLOs at any size
Non-monotonic latency caveat: per-user latency vs B has discontinuities at Nmin-fit transitions (KV outgrows a cluster, forcing more chips). If binary search misses a low-B feasible zone between transitions, the code falls back to an explicit probe at B ∈ {1, 2, 4, 8}.
Mode 2 — Batch / throughput (both SLOs = 0)
Nchips,min
= ⌈ modelbytes / chip.memcap ⌉
clusterHBM
= chip.memcap · Nchips,min
B
= max ( 1 , ⌊ (clusterHBM − modelbytes) / kvper_user ⌋ )
binds
= 'capacity'
No SLO → no latency cap. Fill the cluster's remaining HBM with KV slots; cluster size is fixed at the minimum-fit count.
Output: per-replica chip count
Nchips,required
= Nchips from computeChipSummary(B)
Nchips is a derived output, not a constraint. The "Fits?" column in the comparison table shows this value — the cluster size you'd actually deploy. For total deployment cost at any traffic level, multiply by the number of replicas needed to serve that demand.

11. Key assumptions & caveats

  • Sustained-effective specs, not raw vendor peak. Calibrated against published benchmarks where available (Cerebras ~2000 tok/s/user on Llama 70B, Groq ~250 tok/s/user, etc).
  • 3-year amortization at 24/7 utilization for capex → $/Mcapex. The all-in variant $/Mall-in additionally includes power × PUE 1.3 × $0.10/kWh (US industrial avg power price). Real cloud retail is still 5-50× higher than $/Mall-in (operator margin, redundancy, headroom, cooling, datacenter space, bandwidth, ops headcount).
  • Compute and memory treated as overlapping: per step, time = max(compute_time, memory_time). The standard roofline approximation — real workloads see partial overlap.
  • Tensor parallelism is the modeled scale-out mechanism (no data parallel, pipeline parallel, or sequence parallel for ranking). TP all-reduce is treated as ring (2(N-1)/N × bytes). For latency-bound serving, the calc picks Nchips by SLO: it over-provisions TP beyond the minimum-fit count when that's what production would do (e.g., TP=2-4 on Llama 70B even though 1 H100 fits, because real providers need TP for latency headroom). Inner N-search is capped at 8× minimum-fit or 128 chips. Groq specifically uses pipeline parallelism (PP) rather than TP across its 200-600+ chip deployments; we approximate this by derating Groq's effective mem_bw from raw SRAM read rate (0.128 → 0.065 TB/s, calibrated against published 280 tok/s/user).
  • Continuous batching not modeled: B is treated as a fixed concurrent batch per scenario. Real serving systems (vLLM, SGLang, TensorRT-LLM) have dynamic per-step B and prefix caching; both raise effective throughput.
  • Disaggregated prefill/decode not modeled: real frontier deployments (Mooncake, NVIDIA Dynamo) run prefill on compute-heavy chips and decode on memory-heavy chips. The single-pool model here is a worst case for chips strong on only one axis.
  • No P99 / tail latency: SLO is treated as the mean per-user tok/s. Real production deployments live or die on tail behavior.
  • Speculative decoding not modeled: spec-dec changes the arithmetic intensity of decode (more tokens per memory read), shifting the latency crossover ~1.5-3×.
  • Multi-rack penalty applied as a binary switch: when N_chips > rack_size, the chip's scaleout_bw replaces intra-rack BW for all-reduce / all-to-all. Real fabric topologies (NVL72, Cerebras SwarmX, multi-rack RoCE) have more nuanced behavior.
  • MoE all-to-all assumed bisection-bound: O(N × B × T) per dispatch. On topology-aware fabrics this can be sub-linear, but for most chip selections at hyperscale this is the right model.
  • Costs are public-source estimates only. Real customer pricing varies widely with volume, bundling, direct vs cloud-rental.
  • Model class panels in the frontier use representative models: Small = Llama 3.1 8B, Medium = Llama 3.1 70B, Large dense = Llama 3.1 405B, Large MoE = DeepSeek V3 671B. Workload preset panels use Llama 3.1 70B as the canonical reference.

Workload preset I:O ratios

The I:O ratios in the workload presets reflect typical production traffic for each use case:

  • Chat 1:1 — input prompt ≈ output length in conversational flow.
  • Autocomplete 4:1 — user has typed a few-token query, generates a short completion.
  • Voice 1:1 — speech-to-text-to-speech roughly balanced.
  • Code-assist 5:1 — long codebase context, short inline completion (Cursor / Copilot style).
  • Code-gen 1:2 — short prompt, long generated file. Output-heavy.
  • RAG 10:1 — retrieved passages dominate the prompt; short factual answer.
  • Summarization 30:1 — whole-document input, short summary output.
  • Agentic 20:1 — accumulating tool-use history; sparse intermediate outputs.
  • Batch inference 3:1 — typical labeling / classification — modest prompt, modest output.

Sources for I:O ratios: aggregated from ArtificialAnalysis blog posts on production inference patterns, Anthropic / OpenAI cookbooks, and observed traffic mixes published by major inference providers (Together AI, Fireworks AI, Anyscale). Adjust the I:O ratio input above to test sensitivity.
